<div class="pg-indent"></div><p>装完一个软件，进它文件夹看一眼。三十几个文件平铺在窗口里，名字一多半看不懂。</p><p>你找的那个 exe 在最上面，点得开，用得着。剩下的你能做什么？删一个试试，删错了就开不了机。</p><p>于是关掉窗口。这个文件夹你一辈子不会再看第二次，可它会一直躺在硬盘里，比很多你亲手做的文件活得久。</p><h2>窗口里到底有什么</h2><p>拿一个真的来看。Bandizip 的安装目录，十九个条目，铺开是这样：</p><div 是 dynamic link library，动态链接库。exe 是 executable。这两类名字来自 Windows 之前的 DOS 时代，那时文件名只能是八个字符加三个字符的扩展名。</p><p>八个字符太窄，于是所有厂商都缩写。ark 是「归档」的后半截，bdz 是 Bandizip 的三个首字母，shl 是 shell。</p><p>缩写的本质是给同行看的。写代码的人一天要敲几十遍，没人愿意敲 dynamiclinklibrary。</p><p>你之所以看不懂，是因为这套缩写只在那个圈子里流通。它是内部行话，不是给你准备的说明书。</p><h3>编号与后缀：写给机器排序用</h3><p>64 和 86 是位数。x64 指六十四位，x86 指三十二位，两套并存是因为还要兼容老系统。</p><p>.lgpl 是许可证名，GNU Lesser General Public License 的缩写，意思是这一段代码是开源的，用了别人的东西要标出来。</p><p>.tmp 是临时。带数字的 .1.tmp，意思是第一次临时副本。这类后缀不是人取的，是安装程序在替换文件时自动加的。</p><p>所以一个文件叫 bdzshl.x64.dll.1.tmp，读法不是「随便乱起的名字」，而是：资源管理器右键组件、六十四位、动态链接库、升级留下的第一份临时副本。</p><p>它把四层信息压进二十几个字符。信息全在，就是没打算让人读。</p><h3>大小写与间隔符：写给不同习惯的人用</h3><p>同一个目录里，License.txt 和 LGPL.TXT 并排放着。同一个扩展名，一个大写一个小写。</p><p>在 Windows 上这无所谓，文件系统不区分大小写。可一旦这些文件被拷到 Linux 上，它们就是两个完全不同的名字。</p><p>再往前一步是间隔符的战争。用下划线还是连字符，用空格还是不用，中文名能不能带括号——每个团队都有自己的规矩，规矩之间互不承认。</p><h2>配置为什么散在程序目录里</h2><p>比文件名更让人困惑的是配置。同一个软件，配置可能有三份，分别躺在三个地方。</p><p>一份在程序目录里，比如那个 610 字节的 config.ini。装的时候就写进去，卸载时跟着走。</p><p>一份在用户目录里，比如 AppData 下面某个同名文件夹。这一份才是你在设置界面里改的东西。</p><p>还有一份在注册表里，你在界面上看不到，重装系统时它最先丢。</p><p>这不是设计失误，是历史。早期 Windows 没有给「用户配置」留标准位置，开发者只能往自己目录里塞。</p><p>后来微软补了规范，但老软件已经装出去了，改路径等于让用户重装。所以两套并存，一直并存到今天。</p><p>对照着看更清楚。Linux 世界的 XDG 基础目录规范，一上来就把位置分死了：</p><blockquote><p>$XDG_DATA_HOME 是用户数据文件的唯一基础目录；$XDG_CONFIG_HOME 是用户配置文件的唯一基础目录；$XDG_STATE_HOME 是用户状态数据的唯一基础目录。</p><cite>freedesktop.org《XDG Base Directory Specification》</cite></blockquote><p>数据、配置、状态，三样东西三个家，谁也别往别人家里放。这条规范是 2003 年前后定下来的，到现在还在用。</p><p>Windows 那边其实也有对应的设计意图，但它是后来补的，补的时候已经有一代软件装完了。</p><p>三份并存的实际后果，用过的人大概都碰过一次：改了一处设置，重启之后不生效，因为真正生效的那份在别处。</p><p>或者反过来，卸载了软件，重新装一遍，设置全回来了，因为用户目录里那份没被删。</p><p>这种事解释起来要三句话，感受起来只要一秒：我不懂这台电脑。</p><h2>系统自己留下的垃圾</h2><p>有些名字你根本起不出来。试着新建一个文件叫 CON，Windows 会拒绝。</p><p>不止 CON，还有 PRN、AUX、NUL，以及 COM1 到 COM9、LPT1 到 LPT9。</p><p>微软的命名文档写得很明白：这些名字在任何目录里都是保留的，连加扩展名也不行，NUL.txt 和 NUL.tar.gz 都等同于 NUL。</p><p>原因在 DOS。那时这些名字是设备，CON 是控制台，PRN 是打印机，NUL 是空设备。名字被硬件占了，文件就不许用。</p><p>这套规矩从八十年代留到现在。今天没有谁再用 LPT1 口接打印机，可名字还是保留着。</p><p>所以「目录里的东西都说得清」这句话，从一开始就不成立。连系统自己都在往里面塞说不清的东西。</p><h2>人为什么会想把它们整理好</h2><p>把软件目录按类型重新分文件夹，一晚上搬几百个，第二天软件打不开。这类事在装机圈里很常见，属于反复出现的翻车方式。</p><p>它不说明那个人笨。整理是一种很自然的反应，看到无序就想给它排序，这几乎是本能。</p><p>而且现在有一整套话术在教人这么干。文件名要用日期加项目加版本，目录不超过三层，桌面每周清一次。</p><p>少数派有一篇流传很广的整理术，把命名的作用拆成四条：辨识、区分、管理、定位。</p><blockquote><p>常用的文件命名方法为：文件夹名 = 序列编号-文件夹名，如 01-常用软件、02-系统软件。</p><cite>少数派《工具集 | 超实用的文件整理术》</cite></blockquote><p>这套方法对付自己产出的文件很有效，这一点我不否认。但它有一个前提：这些文件是你造的，你有权改名、有权搬家。</p><p>程序目录不满足这个前提。里面的每个名字都被别的东西引用着，改一个，断一条链。</p><p>把这两种文件混在一起谈，是这类文章最常见的问题。网上流传的那些「桌面零文件」截图也是同一个毛病：拍的是结果，省掉的是维护成本。</p><h2>整理的上限</h2><p>顺带说一句更难听的：即使是对自己的文件，那套整理法也只有一段时间有效。</p><p>有一篇整理类博客讲过一个现象，说很多人花整个周末把几万个文件分得极细，加满标签，不到一个月又乱回去。作者给它起了个名字，叫「过度设计的反扑」。</p><p>这个说法没有学术支撑，是一家工具站的观察，不能当结论用。但它描的那个画面我信：分类系统越精细，维护成本越高，一旦停手几天，它塌得越快。</p><p>塌掉之后人会自责，觉得是自己不够自律。其实不是自律的问题，是这套系统本来就需要一个人全职维护。</p><p>一个人全职维护自己的文件系统，这件事本身就不现实。</p><h2>两种审美</h2><p>这里有一处真分歧，值得摊开说。</p><p>一种审美认为，秩序是能力的证明。桌面干净、目录清楚、命名统一，说明这个人有条理、靠得住。</p><p>另一种审美认为，秩序是成本的别名。每多一层分类，就多一次判断，多一个将来要维护的入口。</p><p>第一种审美在职场里更吃得开，因为它看得见。第二种审美基本看不见，因为它的成果是「什么都没多做」。</p><p>把这两种审美并排摊开，差别其实不在整洁度，而在它们各自默认了什么样的读者。</p><div class="pg-tablewrap"><table><thead><tr><th></th><th>秩序型</th><th>成本型</th></tr></thead><tbody><tr><td>假设的读者</td><td>会来看你目录的人</td><td>将来的你自己</td></tr><tr><td>秩序的作用</td><td>证明你有能力</td><td>缩短找东西的时间</td></tr><tr><td>失败的样子</td><td>被看见的乱</td><td>没人看见的多余劳动</td></tr><tr><td>可见收益</td><td>高，且立刻兑现</td><td>低，且要几个月后才显出来</td></tr></tbody></table></div><p>看这张表的最后一行就知道为什么第一种赢。它的收益当天就能结算，第二种的收益要等很久，而且没人会为此夸你。</p><p>所以第一种审美不只是更受欢迎，它还占据了道德高地：整洁被当成一种品格，不整洁被当成一种缺点。</p><p>这一步跳得太快了。整洁可以是一种习惯、一种偏好、一种职业要求，但它不是品格的证据。</p><p>我不认为第一种是错的。把力气花在展示上，展示本身也是价值，尤其在需要向别人证明自己的场合。</p><p>真正有问题的，是拿第一种审美的标准去衡量所有目录，包括那些你根本没有所有权的。</p><h2>看法的转变</h2><p>如果要说可行的做法，我倾向于三条，都不难。</p><p>程序目录不动。里面的东西不是你的：你不是它的作者，也不是它的用户，你只是装了一下。</p><p>自己产出的文件，只分一层。文件夹叫「在做的」和「做完的」，前者随时会乱，后者基本不再打开。</p><p>剩下的靠搜索。文件名记不全没关系，记得住内容里的一句话就够了。</p><p>这套做法的代价是，永远没有一个漂亮的目录树可以截图。收益是，不用维护它。</p><p>这个交换划算。代价也得认：它换掉的不只是整洁，还有「我很整洁」这件事带来的那点体面。</p><p>所以「看法的转变」这个标题其实有点大。没有转变，只是把原本就不属于你的那部分责任，交还回去。</p><h2>接受平庸这件事</h2><p>回到开头那个窗口。三十几个文件，你一个都读不懂。这件事其实挺伤人的。</p><p>它提醒你：这个你天天在用的东西，它的内部你一点没参与。你只是按了下一步、下一步、完成。</p><p>我们这一代人对「懂」有一种执念。用过的东西要懂原理，做过的事要懂方法，连整理个文件夹都想整理出体系来。</p><p>这套执念有好处，它让人往里钻。但它也有一个没说出口的前提：凡事都该有我一份理解。</p><p>这个前提不成立。世界上的东西太多了，绝大多数你只会用到它的表皮，然后一辈子不再深入。</p><p>承认这一点，不是认输。是承认自己在这件事上就是个普通用户，和几亿人一样，点了下一步，然后用了十年。</p><p>汉典里「平庸」的反义词列了一串：不凡、卓越、优秀、非凡。</p><p>注意这一串里没有「正常」。也就是说，在这套词义系统里，正常本身就等于平庸。</p><p>这不是词的错，是词的用法就这么长出来的。它把「没有超出」直接判成了「低于」。</p><p>所以当有人说要坦然接受平庸，他不是在劝你降低标准。他是在拆一个本来就不成立的等式：没有超出，不等于低于。</p><p>这个题目以前在<a href="/post?id=post-254">坦然接受自己的平庸</a>里正面写过一次，走的是「平庸」这个词在社会比较里的含义。那篇讲人和人之间的位置，这一篇讲人和自己不懂的东西之间的位置。两件事不一样，落到最后是同一句话。</p><p>那句话往回收一步讲，也不算多高明。它只是把一个默认值改回来：你不需要对所有东西都有一份理解。</p><p>你只需要对自己在用它的那部分，有一份够用的把握。</p><p>于是那个窗口关掉，软件继续用十年。中间可能换两次电脑，每次都装一遍，每次都关一次窗口。</p><p>这就是坦然的具体样子，一点也不壮烈。它只是不再花力气去够一件够不着的事。</p><h2>那些文件名其实也是一份简历</h2><p>还有一个角度，我觉得值得摊开。</p><p>一个程序的目录，其实是它二十几年历史的化石层。</p><p>有 2021 年的 FileList.txt，比程序本身还老，没人删。有 x86 和 x64 两套引擎，因为要兼容老机器。有 .lgpl 后缀，因为用了开源代码要标出处。有 .1.tmp，因为某次升级没收尾。</p><p>每一个多余的文件，都是一次妥协留下的痕迹。</p><p>它们不好看，但它们诚实。一个干干净净、每个文件都恰到好处的目录，反倒可能是刚重装过的——历史被抹掉了。</p><p>所以那堆乱七八糟的东西，某种程度上比整洁的目录更接近真实：真实就是一层一层摞上去的将就。</p><p>你不必读懂它们。知道它们是将就摞起来的，就够了。</p><h2>附：相关影像</h2><p>下面这几个视频讲的是怎么给文件夹分类命名。看它们的时候可以留个心：它们教的方法针对的是你自己产出的文件，不是程序目录。</p><div
