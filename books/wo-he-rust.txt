2022 年秋天，群里一个写 Go 的哥们儿半夜甩过来一句：我打算抽空学一下 Rust。我当时正啃着一包薯片，差点没笑出来。心里想的是，又来一个被朋友圈"Rust 是未来"洗脑的。那会儿 Stack Overflow 的调查我其实也翻过，Rust 连续好几年都是"最受喜爱语言"，但"喜爱"和"真用"是两码事——就像大家都说向往西藏，真买票去的没几个。

现在回头看，先被啪啪打脸的是我。

他学了大概一个多月，某天发过来一段代码，是拿 Rust 写了个小工具，几十行，能并发地去抓十几个接口再把结果拼起来——没什么正经用途，就是给他自己那个小项目抓点公开数据。我扫了一眼，没看出什么门道，但他说了句让我有点在意的话："写完之后基本不用管内存，编译器把我可能会犯的错全拦在编译阶段了。"我当时没接话，回去自己搜了搜，越搜越觉得自己像个井底之蛙。

## 第一次被编译器骂

我这个人有个毛病，学新东西喜欢先抄一段能跑的代码，改改看。Rust 我也是这么干的。装好工具链（就一行 curl 命令，这个确实比装 Go 环境还顺），照着教程写了个最基础的：

```rust
let mut s = String::from("hello");
let r1 = &mut s;
let r2 = &mut s;
println!("{} {}", r1, r2);
```

在我以前写 Java 和 Go 的思维里，这有什么问题？我借了两个可变引用，又没同时改，打印一下完事。结果 cargo build 直接给我报红，错误信息大概意思是：你不能在同一作用域里对 s 借出第二个可变引用，因为已经有一个了。

我盯着那个红字看了得有二十分钟。不是看不懂英文，是心里不服。凭什么？我明明只是打印，又没改你的数据。后来才慢慢搞明白，Rust 的规矩简单粗暴到有点不讲理：一个值，要么同时被好多人"只读"地借走（多个 &T），要么只能被一个人"又能读又能改"地借走（一个 &mut T），这两种状态不能共存。官方管这叫 Aliasing XOR Mutability，翻译过来就是"别名和可变，你俩只能活一个"。

当时我骂了句脏话。这不就是强行把我当小白看吗？我写过两年多 Java，都是自己瞎折腾，什么时候因为两个引用同时改一个对象出过事？——哦，其实出过。去年我自己那个小站半夜挂了，查到最后是两个地方都攥着同一个对象的引用，一个正在改，另一个正好读到改了一半的数据。翻了大半夜日志才揪出来。所以我骂完之后，其实有点心虚。

## 所有权这事儿，得用生活里的笨办法想

Rust 最劝退人的概念叫"所有权"（ownership）。教科书式的说法是：每一个值都有一个被称为所有者的变量，当所有者离开作用域，值就被丢弃。听着像绕口令。我自己的笨办法是这样理解的：

你借了朋友一本书。这本书"属于"你，你负责还。你看完了，把书还回去（作用域结束，drop），这很正常。但 Rust 还有个更狠的规矩：书在你手里的时候，你不能说"我把它同时借给另外两个人，还都让他们拿笔在上面划重点"。要么大家都只能看不能划（共享只读），要么只有一个人能看能划（独占可变）。一旦你想划，别人手里的"看"的权限立刻作废。

还有个叫"移动"（move）的东西，第一次见差点把我送走。在 Rust 里，把一个 String 赋给另一个变量，不是复制，是"所有权转移"：

```rust
let a = String::from("hi");
let b = a;
// 这里再用 a 就会编译报错，a 已经不拥有那个字符串了
```

我当时的反应是：哈？我写过两年多代码，赋值还能把原变量弄失效？但这恰恰是为了不让你踩 C++ 那种"浅拷贝完两个指针指向同一块内存，一个释放了另一个变野指针"的坑。Rust 的选择是：宁可让你编译不过，也不让这种事在线上半夜炸。

说实话，刚学那两周我每天都在怀疑人生。写个读文件的小脚本，光是为了让一个字符串能正确地在函数之间传过去又传回来，我能跟编译器较劲一下午。那种感觉就像你本来骑车骑得好好的，突然有人告诉你，从现在起骑车之前要先考一个"平衡证"，而且考官是个一点情面都不讲的机器。

## 它到底解决了什么，让大厂真掏钱

骂归骂，我后来认真想了想：为什么微软、谷歌、Cloudflare 这种级别的公司，是真把 Rust 用在生产环境里，而不是写篇博客喊喊口号？

数字挺吓人的。微软和谷歌都公布过自家的研究：全部安全漏洞里，内存安全相关的占了七成以上。你想想，一个写了二十年的代码库，十次出事有七次是因为"不该访问的那块内存被访问了"——野指针、用完释放了还在用、数组越界。C 和 C++ 性能没得说，但这类 bug 是它们骨子里的老毛病。

Rust 的解法不是在运行时加个垃圾回收器（那样会有停顿，性能敏感的场景受不了），而是把整类错误在编译期就摁死。谷歌给过一组 Android 的数据：从 2019 年到 2024 年，新代码里逐步用 Rust 替代 C++，内存安全漏洞占全部漏洞的比例从 76% 一路掉到 24%。不是少了几个，是腰斩再腰斩。

Cloudflare 那个案例我印象特别深。他们原来用 Nginx 扛流量，Nginx 是多进程模型，每个 worker 各管各的连接，A 进程开的连接 B 进程用不了，结果就是大量重复的 TCP/TLS 握手，费 CPU 也费时间。后来他们用 Rust 写了个叫 Pingora 的代理，基于 Tokio 异步运行时改成多线程，连接池全局共享，实测 CPU 直接降了 70%，内存降了三分之一。对于 Cloudflare 这种体量，省下来的每一分 CPU 都是真金白银的电费和机房成本。

微软那边更绝。他们的 Azure CTO Mark Russinovich 直接公开说，C 和 C++ "应该被认为已过时"，因为微软七成的补丁都在修内存安全漏洞。Windows 的图形接口 GDI 已经塞了三万多行 Rust 进去，核心加密库 SymCrypt 也用 Rust 重写了，目的就是能做形式化验证。

我第一次看到这些材料的时候，心里那点"它就是个玩具语言"的优越感，基本就没了。

## 我拿它干了点什么实事

光看别人吹没用，我自己得动手。我挑了个特别小的练手项目：用 Rust 写个命令行工具，把我那个小站后台接口返回的 JSON 整理成表格打印出来。选它是因为需求简单，但又会碰到"网络请求 + 解析 + 字符串处理"这套组合，够我喝一壶的。

网络请求用了 reqwest，解析用了 serde + serde_json，这两个库在 Rust 生态里算是明星级成熟了。写的过程中有几件事让我路转粉：

一是 cargo 这个工具链真的舒服。cargo new 建项目、cargo add 加依赖（它会自动帮你改 Cargo.toml）、cargo clippy 做比很多项目自带的 lint 还严的检查、cargo fmt 自动格式化、cargo test 跑测试。我以前写 Go 也觉得工具链不错，但 Rust 这套更顺手，一个命令管从头到尾。

二是编译器报错是真的人性化。别的语言报错经常甩你一行看不懂的堆栈，Rust 的报错经常是："你这里借用了 s，但下面第 12 行 s 被移动了，所以这里不能再借。"它甚至会在错误信息里给你画箭头、标行号，有时候还会贴心地来一句"你也许想用 clone()？"。我后来才体会到，为什么很多人说 Rust 新手是被编译器手把手教出来的。

三是异步那套，我是真被 tokio 爽到又被它绕晕过。写那个小工具的时候我顺手加了并发：同时请求五六个接口再合并。用 tokio 的 join! 写起来意外地干净，但理解 future、await 这些概念花了我好几天，因为 Rust 的异步不是语言内置的魔法，而是一套零成本抽象，底层机制你得懂一点，否则报错还是看不懂。

那个小工具最后跑起来了，四十多行核心代码，编译完是个几兆的二进制，丢服务器上直接 ./tool 就能跑，不用装运行时。那一刻我承认，有点爽。

## 生命周期那玩意儿，我是真被绕晕过

前面说的所有权和借用，其实还只是入门。真正让我怀疑自己智商的是"生命周期"（lifetime）标注。

事情是这样的：我想写一个函数，接收一个字符串的引用，再返回它的某个切片，也是个引用。在别的语言里这理所当然，但在 Rust 里，编译器会问你：你返回的那个引用，它指向的数据，到底能活多久？如果调用方手里那个字符串在函数结束时就没了，你返回的引用就成了悬空指针——这正是 Rust 死活不让发生的那种事。

于是你得写成这样：

```rust
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}
```

那个 `'a` 不是什么变量，是个"生命周期参数"，意思是：返回的引用的有效期，和 x、y 里较短的那个绑定。我第一次见到这串符号，脑子里第一反应是"这语言是不是在故意为难人"。但我后来想通了一点：它逼你把"这个引用什么时候会失效"这事儿，在代码里明明白白写清楚，而不是靠运气和约定。C++ 里那些"返回了局部变量的指针"的经典 bug，在 Rust 这儿连编译都过不了。

不过我也得承认，生命周期标错的时候，编译器报的错误经常比问题本身还难懂。它有时候会甩你一大段"help"文字，读了三遍才发现它其实是在说"你这两个引用的生命周期对不上"。那段时间我桌面壁纸都换成了 Rust 官方的生命周期图解，天天看，看得快吐。

## 它和我平时写的 Go，到底差在哪

我平时写得最多的是 Go 和 Python，都是自己玩。Go 也有指针，但 Go 有个垃圾回收器（GC），你不用管内存什么时候释放，运行时帮你收拾。这带来了巨大的省心，代价是偶尔的 GC 停顿——对绝大多数项目来说无所谓，但对那些延迟要精确到微秒的系统，就是个麻烦。

Rust 的卖点恰恰是没有 GC，却又比 C++ 安全。它是怎么做到的？靠的就是前面那套所有权，在编译期就算好了每个值什么时候该释放，生成的机器码里直接插入释放逻辑，运行时不依赖任何后台线程来"打扫"。换句话说，它把 GC 的工作，提前到了编译阶段一次性干完。

我用 Go 写同样的东西，十分钟就能跑起来，但要是哪天我想把它改成高并发、还要绝对不能出 data race 的版本，Go 的 race detector 只能在测试时发现部分问题，Rust 是在编译时就拦。这不是说 Go 不好——Go 胜在简单、上手快、能查到的资料多；Rust 胜在你能写出"几乎不可能在内存和并发上出错"的代码，代价是写的时候累、编译的时候等、学的时候劝退。

我现在的态度特别实际：能三行代码搞定的事，就用 Go 或者 Python，图个省事；但凡涉及"高性能 + 高并发 + 谁写错谁背锅"的核心部分，我会认真考虑 Rust。没必要跟自己较劲非得全程 Rust，也没必要因为怕难就彻底不碰。

## 它真有那么神吗，别被洗脑

但我得说点反话，免得这篇看起来像 Rust 传教文。

它编译是真的慢。项目稍微大一点，cargo build 等得我想去泡杯茶。增量编译好一些，但 clean 之后重新来一遍，那个等待很折磨。而且它的"慢"不只是编译速度，还有你写代码的慢——你得不停地跟编译器商量，很多时候你脑子里的逻辑明明是对的，但就是过不了它的检查，得绕个弯用 clone 或者把生命周期标清楚（那个 'a 的标注，我到现在偶尔还会写错）。

生态也有坑。crates.io 上很多库还停在 0.x 版本，意思是作者随时可能来个 breaking change，你升级一下依赖，代码就炸了。ORM 这块尤其拉胯，diesel 功能强但学习曲线陡，SeaORM 新一点但不如 Java 的 Hibernate 或者 Python 的 SQLAlchemy 成熟。你要是拿 Rust 写那些一天三变的需求、一堆 CRUD，会被它的严谨拖到怀疑人生。真正落地得好的姿势，是像 AWS、Cloudflare 那样：核心的高性能、高并发、安全敏感的那层用 Rust，上层编排用 Go 或者 Python，发挥各自长处。别听谁忽悠"用 Rust 重写一切"，那是在给自己找不痛快。

还有个现实问题：会 Rust 的人不好找。我那个哥们儿后来想找人一起做他的小项目，聊了几个都说太难，卡在生命周期和 trait 上就放下了。这不是语言的问题，是人和时间的问题。

## 没有空指针，也不是靠运气

还有一个让我后来真香的设计，是它对"空"的处理。别的语言里最经典的崩溃来源之一，就是空指针（null pointer）——你以为一个变量有值，结果它是 null，一访问就炸。Tony Hoare 老爷子自己都管 null 叫"十亿美元的错误"。

Rust 里没有 null。它用两个枚举类型替代：Option<T> 表示"可能有值也可能没有"，Result<T, E> 表示"可能成功也可能失败"。你没法假装一个可能不存在的值"肯定存在"，因为类型系统逼你在代码里把"没有"的情况显式处理掉。要么 match 一下分情况，要么用 unwrap（但 unwrap 在确实是空的时候会直接 panic，等于把雷明摆在台面上而不是埋起来）。

这事儿刚接触的时候我觉得啰嗦：不就是个可能为空的值吗，至于让我写这么多分支？后来在 Go 里写多了 if err != nil 之后才回过味来——Go 是让"错误处理"变成每个函数都要写的样板，Rust 是把"可能出错"这件事焊死在类型里，编译期就逼你想清楚。两种哲学，但 Rust 那个更让我安心：你不可能"忘了处理错误"，因为不处理就编译不过。

当然，代价是代码里到处是 match 和 ? 操作符，初看确实比其它语言啰嗦。但啰嗦在这里是 feature，不是 bug。它啰嗦，是因为它不许你偷懒。

## 现在回头看

今年（2024）我又翻了翻，Rust 在 AI 基础设施这块突然又火了一波。大模型推理引擎 candle 是 Rust 写的，Qdrant、SurrealDB 这些向量数据库也是 Rust。逻辑也通：AI 底层那堆对性能、并发、内存安全都极苛刻的引擎，正好是 Rust 的主场。Python 写原型，Rust 写引擎，正在变成一种标配。

当年那个半夜跟我吹 Rust 的哥们儿，去年毕业去了一家做基础架构的公司。前阵子我们视频，我问他后不后悔花那三个月跟借用检查器较劲，他笑着说："后悔个屁，我现在看以前写的 Go 代码，满眼都是潜在的 data race。"

我没接话，但心里是服的。

我自己现在不敢说多懂 Rust，能用它写点小工具、改改别人的 crate 还行，真要撸一个大项目还差得远。但有一点变了：以前我觉得"内存安全"是 C++ 程序员自己该操心的事，跟我用高级语言的无关；现在我明白，那七成的安全漏洞，本来就不该由人来防，该由编译器在门口就拦住。Rust 干的事，说白了就是把"靠自觉"变成"靠强制"。这事儿看着不讲理，但架不住它真的管用。

你要问我一个自己瞎学了几年的人，现在值不值得学 Rust？我的答案是：别冲着"未来语言"这种虚头巴脑的理由去学，也别指望学会了就能接活挣钱。你就找个自己真正想做的小东西，比如我那个破表格工具，逼自己用 Rust 写一遍。被编译器骂个几十回之后，你再看代码，眼光会不自觉地变——会开始想"这块内存谁在管""这个引用会不会有人偷偷改"。这种思维习惯，比学会一门语言值钱多了。

至于那个借用检查器，我现在不骂它了。它不是在刁难你，它只是在替你记着你记不住的那些账。
