我刚学写网页那阵，世界还没这么花。那时候我用 jQuery——一个 `$('button').click(...)` 就能搞定交互的库，简单到让人上瘾。我清楚地记得第一次见到 React 代码时的困惑：为什么改个变量还要套一层 `useState`，为什么页面不让我直接 `document.getElementById('counter').textContent = count`。我本能地觉得"这把简单的事搞复杂了"。后来真用起来，又真被它救过命，才慢慢明白：框架解决的从来不是"能不能做"，而是"项目变大之后，你还做不做得了"。

这篇写给和我一样从刀耕火种过来的前端人，也写给刚入门、被 React、Vue、Svelte 这几个名字绕晕的人。我会把它们的核心差异、背后的原理，和我自己的取舍都摊开讲。

## 没有框架时我们要手写什么

> React is a JavaScript library for building user interfaces.
> —— react.dev 官方文档首页

先把时间拨回去。假设页面上有一个计数按钮，没有框架，你得这么写：声明一个变量 `count`，给按钮绑点击事件，每次点击 `count++`，然后亲手去改 DOM 上那个显示数字的元素。状态（count 是多少）和界面（屏幕上显示几）是分开的，你得自己保证它们一致。

问题就出在"自己保证"上。页面一复杂，状态有十几个，它们之间互相影响，你每改一个状态，就得想清楚"屏幕上的哪几处要跟着变"，漏一处界面就错乱。 jQuery 时代我们管这叫"状态同步的地狱"——不是写不出来，是维护起来心累，改一处牵一发动全身，bug 藏在某个你忘了更新的 DOM 节点里。框架们要解决的，正是"状态变了，界面自动跟上"这件事。

## React 与虚拟 DOM：diff 出最小变更

React 是这一波框架里资历最老、生态最大的。它的核心心法是虚拟 DOM（Virtual DOM）。简单说，框架在内存里维护一棵用 JavaScript 对象表示的"假 DOM 树"。状态一变，它先按新状态生成一棵新树，然后和旧树做"差异比较"（diffing），算出最少需要改哪些真实 DOM 节点，最后只动那几处。你不用再手动找元素、手动改，框架替你把"状态→界面"的同步包办了。

React 用一套叫 Hooks 的东西管理状态，`useState` 存值，`useEffect` 处理副作用，`useMemo`/`useCallback` 做性能优化。数据是单向流动的：数据通过 props 往下传，事件往上抛。"父传子、子调父的方法"这套心智模型，学会之后很清爽。但坦白讲，Hooks 用好并不容易——依赖数组漏写、闭包陷阱，新手踩得鼻青脸肿。这也是很多团队觉得 React "能做的事多，但要学要踩的坑也多"的原因。

从体积看，React 核心加 ReactDOM 大约 40 KB（gzip 后），里面装着协调器（reconciler）和事件系统，每次渲染都要带着这份运行时。它生态的护城河极深——路由、状态管理、UI 组件库，你能想到的几乎都有成熟方案，招人也最好招。对一个技术负责人来说，"大家都会、库最全"本身就是一个压倒性的选型理由。

## Vue：渐进式与编译时优化

Vue 给我的第一印象是"温和"。它不要求你一下子全盘接受它的世界观，可以只在项目里用一小块，慢慢扩。Vue 3 之后主推 Composition API，写法上和 React Hooks 神似：`ref(0)` 定义响应式值，`reactive()` 包裹对象，模板里直接 `{{ count }}`。但它和 React 有个关键不同：Vue 在构建时用编译器把模板优化过一遍，运行时要做的比较比 React 少，等效场景下更省。

Vue 的运行时约 30 KB，靠良好的 tree-shaking 和组合式 API，打包能压得很小。它还有一套很顺手的内置能力：指令（`v-if`、`v-for`、`v-model` 双向绑定）、过渡动画系统、单文件组件（一个 `.vue` 文件里模板、脚本、样式写在一起）。我带新手时，常常先推 Vue，因为"上手快、文档友好、概念不劝退"。它不像 React 那样逼你过早理解函数式那一整套，又能平滑过渡到复杂用法。

我个人用 Vue 写过几个内部工具，最舒服的点是：模板语法贴近 HTML，看得见摸得着，改起来直觉。它不追求"最酷"，追求"大多数人能把它用对"。对一个以交付为目标的个人或小团队，这种"不炫但稳"的气质，其实很值钱。

## Svelte：编译时，没有虚拟 DOM

Svelte 是这三个里最叛逆的。它干脆不要虚拟 DOM。React 和 Vue 是在"运行时"里比较新旧树、再改 DOM；Svelte 反过来，在构建（编译）阶段就把你的组件编译成直接操作 DOM 的命令式代码。你写 `let count = 0`，编译后大概就是 `count++` 时直接 `textContent = count`——没有框架运行时在浏览器里盯着，没有 diff 这一步。

代价和收益都很鲜明。收益是运行时极小，基础运行时只有约 1 到 3 KB（对比 React 的 40、Vue 的 30），首屏和交互速度（Time to Interactive）天生占优，对性能敏感的移动端、首屏尤其友好。写法也极简，几乎不用 import，一个 `$:` 就能声明"依赖变了就重算"的响应式语句。但硬币的另一面是：编译时方案意味着每个组件在打包时都会多带一点自己的代码，项目越大，Svelte 在总体积上的优势会慢慢收窄甚至反超；而且它没有那套"运行时 diff"兜底，局部更新靠编译期分析得准不准。

我的看法是：Svelte 特别适合中小型、讲究轻快的项目，或者你就是想体验"没有框架感"的开发。它证明了"虚拟 DOM 不是必选项"这件事，对整个行业都是一记提醒——框架的进化不一定是指标越来越高，也可以是越来越"消失"。

## 构建工具：Vite 为什么快

聊框架绕不开构建工具，因为它决定了你每天 `npm run dev` 卡不卡。早些年 Webpack 是事实标准，但它慢、配置重，项目一大启动要等半天。2020 年前后 Vite 出现了，打的是"下一代前端工具链"的旗号，靠两招翻身：一是开发时用浏览器原生的 ES Module（ESM）按需加载源码，不用像 Webpack 那样先把整个项目打包一遍，所以启动是秒级；二是热更新（HMR）极快，你存个文件，界面立刻反映，不管项目多大。

Vite 背后早先是 Rollup 做生产打包，后来自研了 Rolldown 进一步提速，插件系统兼容 Rollup 的生态。现在它不只是个工具，更成了"框架底座"——Solid、Svelte、Nuxt、Astro 一大票框架都建在 Vite 之上。我自己的站点就是 Vite 系，最大的体感就是：改完代码不用盯着进度条发呆了。对一个写代码时最怕"等待"的人，这点提升的快乐远超想象。

## 我怎么选：框架只是工具

说到最后，总要落到"那我到底用哪个"。结合我自己的经验，给几句大实话：

如果你是一个人写、项目不大、追求轻快和少依赖，Svelte 或 Vue 都很舒服，前者极致轻，后者生态和文档对新手更友好。如果是团队作战、要招人、要一堆现成库（尤其是中大型应用），React 依然是那个"不会错"的默认项——不是因为它每个指标都赢，而是它的生态和人才池太厚，技术债最小。Vue 则处在中间：比 React 好上手，比 Svelte 更成体系，是很多务实团队的心头好。

但我想强调一件比选型更重要的事：框架是工具，不是信仰。我见过有人为了"用上最新框架"把稳定项目推倒重来，也见过有人死守 jQuery 不肯学新东西。这两种极端我都理解，也都不推荐。我的准则是——用它能让你更快、更稳地交付，而不是让它定义你。真正值钱的，是"状态怎么管、界面怎么跟着变、性能瓶颈在哪"这些底层判断，框架换了一茬又一茬，这些道理不变。

## TypeScript：类型系统如何接住大型前端

聊到框架，绕不开这几年几乎成标配的 TypeScript。它给 JavaScript 加了静态类型——简单说，就是给变量、函数参数、返回值提前声明"你该是什么样"，写错了对齐不了，编辑器当场报错。对于一个几万行、多人协作的前端项目，这点太关键了：改一个接口的字段，所有用到它的地方立刻标红，不用等到上线才炸。

我自己的体会是，小项目用不用 TS 差别不大，但项目一大，TS 就是"接住你"的安全网。它不让你跑得更快，但让你摔得更少。Vue 3 和 React 都原生友好 TS，Svelte 近年也补上了。我的建议是：只要项目会超过几千行、或者会有第二个人碰，就上 TS，早点买这份保险，比事后救火划算。它和框架是正交的两件事——框架管"界面怎么跟着状态变"，TS 管"数据长什么样才对"，两者叠起来，才是现代前端的日常。

## 框架之外的真相：瓶颈往往不在框架

这里有一个很多新手会踩的坑：以为"页面慢"是框架的锅，于是频繁换框架，结果该卡还卡。其实真实的性能瓶颈，绝大多数时候不在框架选了谁，而在更朴素的地方——网络请求太多太慢、图片没压缩没懒加载、打包没做代码分割、长列表没虚拟滚动、一个庞大的第三方库被全量引入。

我见过最典型的浪费：一个展示页引了整个图表库，其实只用了其中一个饼图；或者首屏就把用不到的后台代码全下载了。框架层面，React 的 `React.memo`、Vue 的 `v-memo` 这类优化 API 能帮你控制更新范围，但前提是你先搞清楚"到底哪块在重复渲染"。所以我的判断一直很直接：先量（用开发者工具看长任务、看网络瀑布），再优化，别凭感觉甩锅给框架。框架之间的性能差距，在真实项目里往往小到用户根本感知不到；而一次图片优化、一个懒加载，带来的提升可能顶得上换三次框架。

## 我踩过的一次"无意义迁移"坑

说句掏心窝的。有一年我手痒，把团队一个稳定运行的项目从 Vue 迁到了 React，理由是"React 生态更大、招聘更容易"，听起来很理性。结果迁移本身花了一个多月，过程中 bug 不断，上线后用户体验没有任何可感知的提升，反而因为新代码不熟，出过几次本不该出的事故。那次之后我给自己立了规矩：要不要换框架，只看"现有框架是不是真的卡住了你"——是维护成本失控？是招不到人？是某个必需能力它真没有？如果都不是，就别动。框架迁移的隐性成本（重写、回归测试、团队重新适应）经常被低估，而显性收益常常为零。技术上的"喜新厌旧"，是比用旧框架更贵的病。

## 收尾

回到开头那个困惑：React 把我从"手写 DOM 同步"里解放出来，代价是学一套新心智。现在回头看，那不是把简单变复杂，是把"项目膨胀后的复杂"提前标准化了。我那个用 jQuery 的 young self 如果看到今天一个几万行的应用还能被清晰地组织，大概会承认：有些复杂，是成长必须交的学费。而我，已经学会了在学费和收益之间，自己拿主意。
